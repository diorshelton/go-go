TCP & Connections

Before you can parse an HTTP request, you need to understand what's delivering those bytes to your program. That's TCP — and understanding it changes how you think about everything above it.

What is a connection, actually?

When someone says "the client sends a request to the server," that description skips over what actually happens. There's no single moment where bytes are teleported from one machine to another. Instead, a connection is established first — a dedicated channel between two endpoints — and then bytes flow through it.

That channel is a TCP connection. TCP stands for Transmission Control Protocol, and it has one job: guarantee that bytes sent from one end arrive at the other end, in order, without duplication. It handles retransmission, ordering, and flow control so you don't have to.

Why this matters for go-go
In go-go, your server calls net.Listen and then Accept() in a loop. Each call to Accept() returns one TCP connection — one of these dedicated channels. Everything you do afterward (reading bytes, parsing the request, writing a response) happens on that single connection.

The connection as a pipe

The most useful mental model: a TCP connection is a bidirectional pipe. Once it's open, you can write bytes into one end and they come out the other, in the same order, with no gaps. The pipe stays open until one side closes it.

Client
──── bytes flow this way ────→
←─── bytes flow this way ────
Server (your go-go process)

This is important: the pipe is persistent. You don't open and close it for every chunk of data. HTTP/1.1 takes advantage of this — multiple requests can travel over the same connection, one after another. That's what keep-alive is. But we'll get there in Module 2.

How Go exposes this

Go's net package wraps TCP connections behind the net.Conn interface. Once you have one, you interact with it using two methods you already know from other contexts:

type Conn interface { Read(b []byte) (int, error) // pull bytes from the pipe Write(b []byte) (int, error) // push bytes into the pipe Close() error // close the pipe // ... plus deadline methods }

Read blocks until bytes arrive. Write sends bytes. Close tears down the connection. That's the entire API surface you'll be working with in listener.go and parser.go.

One connection, one goroutine

Here's a design question you'll need to answer when building go-go: if Read blocks until bytes arrive, and your server needs to handle many connections at once — what's your strategy?

The naive answer is: spawn a goroutine per connection. And for many servers, that's fine. But go-go uses a fixed worker pool instead. There's a reason for that choice, and it's one of the first things worth thinking through carefully.

Think it through
If Read blocks — it just sits there waiting for bytes — what problem does that create if you handle connections one at a time in a single loop?
Imagine 100 clients connect simultaneously. Connection #1 is slow. What happens to connections #2 through #100?
The server stalls. If you handle connections sequentially — accept one, read from it until it closes, then accept the next — then a slow or idle client blocks every other client. Connection #2 can't be served until connection #1 finishes.

This is why concurrency is necessary: you need to be able to Read from many connections simultaneously without any one of them blocking the others. Goroutines are Go's answer to this. But if you spawn one goroutine per connection with no limit, you have a different problem — what happens if 100,000 clients connect?
Think it through
go-go uses a fixed worker pool — N goroutines total — instead of spawning a new goroutine for every connection. What does that limit protect against?
Think about what happens to memory and scheduling overhead when you have a very large number of goroutines.
Unbounded resource consumption. Goroutines are cheap, but not free — each costs a few KB of stack memory, and the scheduler has to manage all of them. If 100,000 clients connect simultaneously and you spawn 100,000 goroutines, you burn through memory fast and the scheduler's overhead becomes significant.

A fixed pool caps this. You decide upfront: this server will use N goroutines, no more. If more connections arrive than the pool can handle, they wait in a channel. You trade some latency under extreme load for predictable, bounded resource usage. That's the explicit, observable concurrency model the SPEC describes.
