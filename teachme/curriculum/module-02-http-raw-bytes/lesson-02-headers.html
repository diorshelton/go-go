Headers Over the Wire

After the request line come the headers — a series of key:value pairs that describe metadata about the request. Your parser reads them line by line until it hits a blank line. That blank line is load-bearing.

The full structure on the wire

PUT /keys/foo HTTP/1.1 \r\n Host: localhost:8080 \r\n Content-Type: application/json \r\n Content-Length: 15 \r\n Connection: keep-alive \r\n   \r\n ← blank line: headers done, body follows {"value":"bar"}

The structure is rigid: Name: value\r\n. The separator is a colon followed by optional whitespace. The terminator is always CRLF. When you read a line that is just CRLF (or an empty string after stripping), headers are done.

Parsing headers in Go

headers := make(map[string]string) for { line, err := reader.ReadString('\n') if err != nil { return nil, err } line = strings.TrimRight(line, "\r\n") if line == "" { break // blank line = end of headers } idx := strings.IndexByte(line, ':') if idx < 1 { return nil, errors.New("malformed header") } key := strings.ToLower(strings.TrimSpace(line[:idx])) val := strings.TrimSpace(line[idx+1:]) headers[key] = val }

Two things to call out:

  • strings.ToLower on the key — HTTP header names are case-insensitive by spec. Normalizing to lowercase lets you look them up consistently: headers["content-length"] works whether the client sent Content-Length, content-length, or CONTENT-LENGTH.
  • idx < 1 check — rejects lines with no colon (idx == -1) or a colon as the very first character (idx == 0, which would make the key empty).

The headers that matter for go-go

Of all the headers a client might send, only two are relevant to your server's behavior:

// How many bytes is the body? contentLength, _ := strconv.Atoi(headers["content-length"]) // Should we keep the connection open after responding? keepAlive := strings.ToLower(headers["connection"]) != "close"

Content-Length tells your parser how many body bytes to read. Without it, you don't read a body. Connection tells your worker loop whether to wait for the next request on this connection or close it after responding.

HTTP/1.1 default: keep-alive
In HTTP/1.1, connections are persistent by default. A client that sends no Connection header expects the connection to stay open. Only when it sends Connection: close does it signal that it won't send more requests. Your worker loop must handle both cases.

The blank line is a boundary, not punctuation

It's easy to think of the blank line as just formatting — a visual separator. It isn't. It's the only thing that tells your parser where headers end and body begins. If a client sends a header with a missing CRLF, or skips the blank line, your parser reads the body as a header (or keeps reading expecting more headers indefinitely). This is an attack vector — HTTP request smuggling exploits ambiguity in exactly this boundary.

For go-go, the defense is simple: if you don't find a blank line within a reasonable read (bounded by a max header count or read timeout), return 400.

Set a read deadline before parsing
A client that connects and sends nothing will leave your parser blocking on ReadString('\n') forever — holding a worker goroutine doing nothing. Set conn.SetReadDeadline(time.Now().Add(30 * time.Second)) before each read cycle. If the deadline fires, ReadString returns a timeout error, and you close the connection. No goroutine leaks.
Think it through
Why normalize header keys to lowercase rather than preserving their original case?
Different HTTP clients send Content-Type, content-type, CONTENT-TYPE. How do you look up a header reliably if you preserve case?
Case-insensitive lookup requires normalization. If you store headers as-received, a lookup for content-length will miss a header stored as Content-Length. You'd need to do a case-insensitive comparison every time. Normalizing at parse time (ToLower once) makes all subsequent lookups simple map gets. The spec explicitly says header field names are case-insensitive, so normalization is correct behavior.
Think it through
A client sends 500 headers in a single request. What should your parser do?
There's no hard limit in the HTTP spec. But should you parse all 500?
Return 431 (Request Header Fields Too Large) after a reasonable limit. An unbounded header loop is a denial-of-service vector — a client can flood your parser with headers, tying up a worker goroutine and memory. Real servers cap headers (nginx defaults to 80, Apache to ~100). For go-go, a cap of 50–100 is reasonable. Count headers in your loop and return 431 if the count exceeds your limit.
