The Body & Content-Length

After the blank line come the body bytes — but only if the request has them, and only if you know exactly how many to read. Content-Length is the contract. Break it, and you'll either block forever or corrupt the next request.

When does a request have a body?

In HTTP/1.1, the body is optional and its presence is determined by headers — not by the method. For go-go specifically:

  • GET /keys and GET /keys/:id — no body. The request is complete after the blank line.
  • DELETE /keys/:id — no body. Same.
  • PUT /keys/:id — has a body. The JSON value for the key is in the body.

Your parser's rule: if Content-Length is present and greater than zero, read that many bytes. Otherwise, don't read any body bytes at all.

Reading exactly N bytes

var body []byte clStr := headers["content-length"] if clStr != "" { n, err := strconv.Atoi(clStr) if err != nil || n < 0 { writeError(conn, 400, "Bad Request") return } if n > maxBodySize { writeError(conn, 413, "Content Too Large") return } body = make([]byte, n) _, err = io.ReadFull(reader, body) if err != nil { writeError(conn, 400, "Bad Request") return } }

The key function here is io.ReadFull. Unlike a plain Read call (which might return fewer bytes than requested), ReadFull blocks until it has read exactly N bytes or encounters an error. This is the right primitive for body reading.

Why not just use Read()?
TCP doesn't guarantee that bytes arrive all at once. A client sending 500 bytes might have them arrive in two chunks: 300 bytes, then 200 bytes. A single Read() call might return only 300. io.ReadFull loops internally until it has all N bytes, handling partial reads for you.

json.RawMessage — why go-go uses it

The value in a PUT request is arbitrary JSON: a string, number, object, array. Your cache stores it and returns it unchanged. You don't need to parse it — just preserve it.

json.RawMessage is []byte under the hood, but it satisfies the json.Marshaler and json.Unmarshaler interfaces in a way that means "don't re-encode me — I'm already JSON." When you store the body as a json.RawMessage and later marshal it into a response, it gets written verbatim. No double-encoding, no loss of precision on numbers.

// In the handler: store.Set(id, json.RawMessage(body)) // In the cache (store.go): type Store struct { mu sync.RWMutex data map[string]json.RawMessage }

Body size limits

A client that sends Content-Length: 999999999 would cause your parser to allocate 1GB of memory for the body. You need a cap. Define a maxBodySize constant (1MB is reasonable for go-go) and return 413 Content Too Large if exceeded.

Never read more than Content-Length says
If you read past the end of the body on a keep-alive connection, you'll consume the start of the next request. The next parse cycle will start with garbage. This is a real class of bug in production HTTP servers. Read exactly N bytes, no more.
Think it through
A PUT request arrives with Content-Length: 15 but only 10 bytes are in the body. What does io.ReadFull do, and what should your parser do with that error?
The client disconnected mid-send, or sent a wrong Content-Length.
io.ReadFull returns an error (io.ErrUnexpectedEOF). It tried to read 15 bytes but the connection closed after 10. Your parser should return 400 Bad Request. You cannot proceed — you don't have a complete body. The connection is likely dead anyway, but you should call conn.Close() explicitly to be sure. Don't try to use the partial body.
Think it through
A GET request arrives with a Content-Length: 20 header. Should your parser read 20 body bytes?
The HTTP spec says GET requests may have a body. Should go-go honor that?
For go-go, no — reject it with 400. While the HTTP spec technically allows GET requests to carry a body, it has no defined semantics for it, and many servers (and proxies) reject or ignore it. Since go-go's GET handlers don't expect or use a body, accepting one creates ambiguity without benefit. The simpler rule: methods with no defined body semantics (GET, DELETE) get 400 if they send Content-Length.
