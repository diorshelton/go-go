listener.go — Accepting Connections

Module 4 is where the theory becomes implementation. Each lesson walks through one component of go-go — its responsibilities, its design decisions, and the traps to avoid. You'll implement each one in the corresponding exercise.

What listener.go is responsible for

Exactly three things:

  1. Open the TCP listener on the configured port
  2. Accept connections in a tight loop and hand them to the pool
  3. Handle shutdown: stop accepting, drain workers, exit cleanly

Nothing else. No parsing, no routing, no responding. The listener's job ends the moment a connection is sent to the pool.

The complete implementation

package server import ( "net" "os" "os/signal" "syscall" ) func Run(port string, workers int, store *cache.Store) { ln, err := net.Listen("tcp", ":"+port) if err != nil { log.Fatalf("listen: %v", err) } router := NewRouter(store) pool := pool.New(workers, router) // Catch interrupt/terminate signals to shut down gracefully quit := make(chan os.Signal, 1) signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM) go func() { <-quit ln.Close() // unblocks Accept() }() // Accept loop — this is the only thing happening here for { conn, err := ln.Accept() if err != nil { break // listener closed — shut down } pool.Submit(conn) } pool.Shutdown() // close channel, wait for workers }
Why a goroutine for the signal handler?
Signal handling blocks on <-quit. If you handle it in the main goroutine, you can't also run the accept loop there. So the signal handler runs in its own goroutine, waiting for the signal. When it arrives, ln.Close() is called, which causes Accept() in the main goroutine's loop to return an error. The two goroutines communicate through the listener's state, not through a shared variable.

What the pool.Submit call looks like under load

When all workers are busy and the channel buffer is full, pool.Submit(conn) blocks. During this time, Accept() is not being called. The OS backlog queue starts filling up. When the backlog is full, new incoming SYN packets are dropped by the OS — clients see a connection timeout.

This is intentional. It's the server communicating to the network that it's at capacity. The alternative — accepting all connections regardless — would mean allocating unbounded goroutines and memory, which fails less gracefully.

Think it through
After the signal handler calls ln.Close(), the accept loop exits. But the pool still has connections being handled. What prevents the process from exiting before those connections finish?
pool.Shutdown() and the WaitGroup. After the accept loop breaks, pool.Shutdown() closes the connection channel (signaling workers) and then calls wg.Wait(), which blocks until all workers have finished their current connections and called wg.Done(). Only then does Shutdown() return and Run() exit.
