Module 03 · Exercise 01

Design the Worker Pool

This exercise walks you through the design decisions behind go-go's worker pool using Socratic questions. Each question forces you to reason about a specific trade-off before seeing the answer. Work through them in order — they build on each other.

The skeleton

Here's the incomplete pool implementation. The questions walk through what goes in the blanks and why each decision was made:

type Pool struct { connCh chan net.Conn wg sync.WaitGroup router *Router } func New(workers int, router *Router) *Pool { p := &Pool{ connCh: make(chan net.Conn, ???), // Q1: what size? router: router, } for i := 0; i < workers; i++ { p.wg.Add(1) go p.worker() } return p } func (p *Pool) Submit(conn net.Conn) { ??? // Q2: what goes here? } func (p *Pool) worker() { defer p.wg.Done() for conn := range p.connCh { handleConn(conn, p.router) } } func (p *Pool) Shutdown() { ??? // Q3: what goes here? p.wg.Wait() }
Question 1
What should the channel buffer size be — the ??? in make(chan net.Conn, ???)?
Consider: what is the maximum number of connections that could be "in flight" between Submit() and a worker picking them up?
workers. At any moment, the accept loop could have submitted up to workers connections before any worker finishes its current one. Buffering to workers means the accept loop can always submit a new connection for each idle-worker slot, absorbing a natural burst. A larger buffer wastes memory; a smaller one (including 0) causes the accept loop to block earlier than necessary.
Question 2
What goes in Submit()? Just p.connCh <- conn?
What happens to Submit() when the pool is shutting down and the channel is closed? Can a send to a closed channel panic?
For go-go's simple case: yes, just p.connCh <- conn. The accept loop exits before Shutdown() is called, so Submit() is never called on a shutting-down pool. But in a more robust implementation, you'd use a select with a done channel to handle the shutdown-races-with-submit case without panicking. For now: p.connCh <- conn is correct given the shutdown ordering we enforce.
Question 3
What goes in Shutdown() before p.wg.Wait()?
Workers loop on range connCh. What signals them to stop?
close(p.connCh). When you close the channel, the range loop in each worker exits after draining any remaining connections. Workers don't stop immediately — they finish whatever connection they're handling, then exit the range loop, then call wg.Done(). wg.Wait() then waits for all of them to finish. The close must happen before Wait() — otherwise the workers never exit their range loop and Wait() blocks forever.
Question 4
Why is wg.Add(1) called in New() rather than inside the goroutine itself?
What could go wrong if wg.Add(1) were the first line inside the go func()?
Race between Add and Wait. If Add(1) is inside the goroutine, there's a window between when go func() is called and when the goroutine actually starts executing. If Shutdown() is called in that window, wg.Wait() might return before the goroutine has called Add(1), causing the shutdown to complete with goroutines still running. Adding before the goroutine starts eliminates this race.
Synthesis question
Explain the full shutdown sequence in order. What must happen first, second, and third?
Think about: listener, accept loop, channel, workers, WaitGroup.
1. Close the listener. This causes the accept loop's Accept() to return an error.

2. Accept loop exits. It detects the error, breaks out of the for loop, and never calls Submit() again.

3. Call pool.Shutdown(). This closes the connection channel, signaling workers to drain and exit their range loops.

4. wg.Wait() blocks until all workers call wg.Done().

5. Process exits cleanly. No goroutines are leaked. No connections are abandoned mid-response.
