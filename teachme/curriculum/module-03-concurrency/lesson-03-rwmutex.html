RWMutex — Concurrent Reads vs Exclusive Writes

Your in-memory cache is a Go map. Multiple worker goroutines read and write it simultaneously. Without coordination, that's a data race — undefined behavior in Go. sync.RWMutex is the solution, and its design reflects a fundamental insight about read vs write access.

Why a plain mutex isn't enough

A sync.Mutex allows only one goroutine at a time — reads and writes alike. That's correct, but overly conservative. Two goroutines doing simultaneous reads of the same map can't corrupt each other — reads don't modify state. Blocking them from running in parallel wastes throughput.

An RWMutex distinguishes between two kinds of locks:

  • Read lock (RLock/RUnlock): multiple goroutines can hold it simultaneously
  • Write lock (Lock/Unlock): exclusive — no other goroutine (reader or writer) can hold any lock while a write lock is held

Read lock✓ allowed — concurrent reads are safe✗ blocked — wait for readers to finish
Write lock✗ blocked — wait for writer to finish✗ blocked — wait for writer to finish
No lock✓ allowed✓ allowed

The cache implementation

type Store struct { mu sync.RWMutex data map[string]json.RawMessage } func (s *Store) Get(key string) (json.RawMessage, bool) { s.mu.RLock() defer s.mu.RUnlock() v, ok := s.data[key] return v, ok } func (s *Store) Set(key string, val json.RawMessage) { s.mu.Lock() defer s.mu.Unlock() s.data[key] = val } func (s *Store) Delete(key string) { s.mu.Lock() defer s.mu.Unlock() delete(s.data, key) } func (s *Store) Keys() []string { s.mu.RLock() defer s.mu.RUnlock() keys := make([]string, 0, len(s.data)) for k := range s.data { keys = append(keys, k) } return keys }

The pattern: RLock() before reading, Lock() before writing. Always paired with the corresponding Unlock, always deferred so panics don't leave locks held.

Why defer for Unlock?
If your handler panics between Lock() and Unlock() and you don't defer, the lock is never released. Every subsequent goroutine trying to acquire the lock will block forever — a deadlock. defer s.mu.Unlock() guarantees the unlock happens even if the function exits via panic.

Never hold a lock while doing I/O

A common mistake: lock the mutex, read from the cache, then write the response to the connection — all while holding the lock. This serializes all responses to the same lock, crushing throughput.

// WRONG — holding lock across I/O s.mu.RLock() val := s.data[key] conn.Write(val) // slow I/O while holding lock! s.mu.RUnlock() // CORRECT — release lock before I/O s.mu.RLock() val := s.data[key] s.mu.RUnlock() // release immediately conn.Write(val) // then do I/O

Hold locks for the minimum time necessary: acquire, access the shared data, release, then do whatever else needs doing.

Never copy a mutex
A sync.RWMutex must not be copied after first use. If you pass a Store by value, its mutex is copied — and the copy has independent lock state, defeating the whole purpose. Always pass *Store (pointer), never Store (value).
Think it through
10 goroutines all call store.Get(key) simultaneously. How many of them are blocked?
They all call RLock(). What does the compatibility matrix say about concurrent read locks?
None. All 10 goroutines acquire the read lock simultaneously and proceed in parallel. RLock is compatible with other RLocks — that's the entire point of RWMutex. If you used a plain Mutex, 9 of the 10 would block. RWMutex optimizes for the common case in a read-heavy cache: reads are fast and parallel, writes are exclusive but rare.
Think it through
A goroutine calls store.Set(key, val). At the same moment, 10 goroutines are in the middle of store.Get(key). What happens?
The writer wants a write lock, but readers are holding read locks. What does the write lock do?
The writer blocks until all readers finish. Lock() waits until all existing RLocks are released. While the writer is waiting, no new readers can acquire RLock either (this prevents reader starvation of writers). Once all 10 readers call RUnlock(), the writer acquires the exclusive write lock, modifies the map, and releases. Then any new readers can proceed.
