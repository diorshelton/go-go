Worker Pools — Bounded Concurrency

A worker pool is a fixed set of goroutines that pull work from a shared channel. It's the pattern behind go-go's connection handling — predictable resource usage, no goroutine proliferation.

The pattern

Three components:

  1. A work channel — connections are sent here by the accept loop
  2. N worker goroutines — each loops on the channel, processing one connection at a time
  3. A WaitGroup — used to wait for all workers to finish before the process exits
func startPool(n int, connCh <-chan net.Conn, router *Router) *sync.WaitGroup { var wg sync.WaitGroup for i := 0; i < n; i++ { wg.Add(1) go func() { defer wg.Done() for conn := range connCh { handleConn(conn, router) } }() } return &wg } // In main / Run(): connCh := make(chan net.Conn, workers) wg := startPool(workers, connCh, router) // ... accept loop runs ... close(connCh) // signal workers to stop wg.Wait() // wait for all to finish

How the pool handles backpressure

When all N workers are busy handling connections, the channel buffer absorbs a small burst. When the buffer is also full, the accept loop's channel send blocks — it can't accept any more connections until a worker finishes. This is natural backpressure: the system slows at the input (accept loop) when it's at capacity, rather than growing without bound.

This is the fundamental difference between a pool and spawning one goroutine per connection: the pool enforces a limit. Under load, new connections wait instead of causing the server to allocate memory unboundedly.

The WaitGroup's purpose
wg.Wait() ensures that when the process is shutting down, it waits for all workers to finish their current connections before exiting. Without it, the process might exit with workers mid-response — truncating responses and confusing clients. wg.Add(1) is called before the goroutine starts; wg.Done() is deferred inside it.

A subtle bug: capturing loop variables

This is a classic Go mistake in pool code:

// WRONG — in older Go versions (pre-1.22) for i := 0; i < n; i++ { go func() { fmt.Println(i) // all goroutines see the same i }() }
// CORRECT — pass i as a parameter for i := 0; i < n; i++ { go func(id int) { fmt.Println(id) // each goroutine gets its own copy }(i) }

In go-go's pool, there's no loop variable used inside the goroutine — it only receives from the channel — so this isn't an issue. But it's important to recognize for general Go work.

Don't add to the WaitGroup inside the goroutine
wg.Add(1) must be called before starting the goroutine, not inside it. If you call wg.Add inside the goroutine, there's a race: wg.Wait() might return before the goroutine has even had a chance to call wg.Add. Always Add before go.
Think it through
A worker pool has 10 goroutines. 10 slow connections arrive simultaneously — each takes 30 seconds. What happens to connection #11 when it arrives at second 5?
All workers are busy. The channel buffer is full. What does the accept loop do?
The accept loop blocks on the channel send. With all workers busy and the buffer full, the channel send in the accept loop blocks. The accept loop cannot call Accept() again until a worker finishes. Connection #11's TCP handshake has already completed (it's in the OS backlog queue), but your application code doesn't dequeue it yet. When connection #1 finishes at second 30, a worker becomes free, the channel send unblocks, connection #11 is dequeued and handed off. The client waited 25 extra seconds — but no goroutines were leaked and memory stayed bounded.
Think it through
What's the right value for the pool size (N)? How would you think about it?
go-go sets it via a --workers flag. What factors should inform the choice?
It depends on the workload. A good starting point is the number of CPU cores (runtime.NumCPU()), since workers can only run in parallel up to that count. But go-go's workers spend most of their time blocked on I/O (waiting for bytes to arrive), not on CPU. For I/O-bound work, you can have more workers than CPUs — they mostly block, freeing CPUs for others. A common heuristic: 2–4× CPU count for I/O-bound servers. The --workers flag makes this tunable so you can measure and adjust.
