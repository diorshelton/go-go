Build a TCP Echo Server

Before you write an HTTP server, write something simpler: a server that accepts a TCP connection, reads whatever the client sends, and writes it straight back. This forces you to use the exact primitives — net.Listen, Accept, Read, Write — before any HTTP complexity is layered on top.

Goal
A TCP server on port 9000. Any client that connects can type text and see it echoed back, line by line. When the client disconnects, the server handles it cleanly and waits for the next client.

Setup

Create a new directory outside the go-go project for this exercise:

$ mkdir echo-server && cd echo-server
$ go mod init echo
$ touch main.go

You'll write everything in main.go. No external packages — just net, bufio, fmt, and log from stdlib.

Build it in steps

1
Start the listener
In main(), call net.Listen("tcp", ":9000"). Handle the error. Defer ln.Close(). Print a message so you know it's running.
2
Accept in a loop
Add a for loop that calls ln.Accept(). On error, break. On success, call a handleConn(conn net.Conn) function. For now, call it directly (not in a goroutine) — you'll see why concurrency matters in the next step.
3
Implement handleConn
In handleConn: defer conn.Close(). Use a bufio.Scanner to read line by line. For each line, write it back using conn.Write(). When the scanner returns false (client disconnected), return.
4
Test it
In one terminal: go run main.go. In another: nc localhost 9000 (netcat). Type anything — you should see it echoed back.
Observe this
Open two terminals and try connecting two netcat sessions simultaneously to your server. What happens to the second one?
Show answer
The second client blocks until the first disconnects. Because handleConn is called directly (not in a goroutine), the accept loop is stuck waiting for the first connection to finish. The second client's TCP handshake completes (it's in the OS backlog), but your code never calls Accept() to hand it off. Now you understand concurrency at the network level — not just in theory.
5
Fix it with a goroutine
Change the direct call to go handleConn(conn). Re-test with two simultaneous netcat connections. Both should echo independently. This is the simplest version of concurrent connection handling — and exactly the starting point that go-go improves on with a bounded worker pool.

Challenge extensions

Challenge 1
Add a connection counter. Print how many active connections exist when each new client connects and disconnects.
Hint: you'll need sync/atomic or a mutex to safely increment/decrement from multiple goroutines.
Challenge 2
Add a read deadline. If the client sends no data for 30 seconds, close the connection. Use conn.SetReadDeadline(time.Now().Add(30 * time.Second)) before each read.
Hint: a deadline error from Read() is not a panic situation — detect it and close cleanly.
Challenge 3 — Worker pool
Replace the unbounded go handleConn(conn) with a fixed pool of 3 worker goroutines using a channel. Observe what happens when 4 clients connect simultaneously.
This is exactly the pattern in go-go's pool.go — implement it here first in a simpler context.
Reflect before moving on
What would you need to change about this echo server to make it speak HTTP instead of raw text?
Show answer
You'd need to parse HTTP. Right now handleConn reads whatever bytes arrive and echoes them. To speak HTTP, you'd need to:

1. Read bytes until you find a valid HTTP request (request line + headers + blank line)
2. Parse those bytes into a structured request (method, path, headers, body)
3. Route the request to a handler
4. Write a valid HTTP response (status line + headers + body)
5. Loop back to step 1 if the connection is keep-alive

That's exactly what Modules 2, 3, and 4 build — in that order.
