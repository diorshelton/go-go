The 3-Way Handshake

Before a single byte of HTTP data moves, TCP establishes the connection. This takes exactly three messages — no more, no less. Understanding this tells you what Accept() is waiting for and what state the connection is in when it returns.

Why a handshake at all?

TCP is a reliable, ordered protocol. To deliver those guarantees, both sides need to agree on a starting state before any data flows. Specifically, each side needs to tell the other its starting sequence number — the counter it uses to order bytes — and the other side needs to acknowledge it. That negotiation is the handshake.

You don't control any of this from application code. The OS kernel and Go's net package handle it completely. But knowing it happened tells you something important: by the time Accept() returns a net.Conn, the handshake is already done. The connection is fully established. You're not racing anyone.

After the ACK, both sides have established sequence numbers, both sides know the other is alive, and data can flow. The next bytes the client sends are application data — in go-go's case, an HTTP request.

The listen backlog

Here's something important that happens before Accept() is called: the OS maintains a backlog queue of completed connections — connections that have finished the handshake but haven't been handed to your application yet.

When you call net.Listen, you're telling the OS to start accepting incoming connection requests and queueing them. When you call Accept(), you're dequeuing one completed connection from that queue. If the queue is empty, Accept() blocks.

This is why your accept loop matters: if you accept connections slowly, that queue fills up. New connection requests get dropped by the OS. Your accept loop must be tight — accept the connection and immediately hand it off to a worker, never do slow work in the accept path.

What this means for listener.go
Your Accept() loop should do exactly two things: call Accept(), then send the connection to the worker pool channel. Nothing else. Parsing, reading, and responding all happen in the workers — never in the accept loop.

What Go handles for you

When you call net.Listen("tcp", ":8080"), Go:

  • Creates a socket and binds it to port 8080
  • Calls the OS listen syscall with a default backlog size
  • Starts the OS's connection acceptance machinery

When a client connects, the OS handles the SYN, sends the SYN-ACK, and waits for the ACK — all in kernel space, invisible to your code. By the time Accept() returns, that work is done. You get a fully-established net.Conn.

Think it through
After Accept() returns a net.Conn, is it possible that the connection is not yet established — that the handshake is still in progress?
Think about when in the sequence Accept() returns relative to the three handshake messages.
No. Accept() only returns after a connection has moved from the backlog queue into your application. A connection is only placed in the backlog queue after all three handshake messages are complete — after the OS receives the final ACK. So when you get a net.Conn from Accept(), the connection is fully established. You can immediately call Read() and expect data.
Think it through
Why is it critical that your accept loop hands connections off quickly rather than doing any work inline?
Think about the backlog queue and what happens when it fills up.
Backlog overflow drops new connections. The OS backlog queue has a fixed capacity. If you're slow to call Accept() — because you're doing parsing or I/O in the accept loop — the queue fills up. When it's full, the OS starts rejecting new SYN packets. Those clients get a connection refused error before your application ever sees them. The fix is to accept immediately and defer all work to goroutines or a worker pool.
