net.Listen & the Accept Loop

This is where the concepts from Lessons 1 and 2 become code. We'll walk through the exact Go patterns that power listener.go — the entry point of every connection your server handles.

Starting the listener

Two lines of Go are all it takes to open a TCP port:

ln, err := net.Listen("tcp", ":8080") if err != nil { log.Fatal(err) } defer ln.Close()

net.Listen binds to port 8080 and tells the OS to start queueing incoming connections. It does not start accepting them — that's your job. The defer ln.Close() is critical: when your process exits, this closes the listener and releases the port.

The accept loop

Once you have a listener, you sit in a loop calling Accept():

for { conn, err := ln.Accept() if err != nil { // ln.Close() was called — time to shut down return } connCh <- conn // hand off to worker pool, don't block here }

Accept() blocks until a connection is ready, then returns it. When ln.Close() is called (for shutdown), Accept() returns an error — that's your signal to exit the loop cleanly.

The only rule of the accept loop
Accept immediately, hand off immediately. The two operations on each iteration are Accept() and a channel send. That's it. Any work you do inline here — reading, parsing, logging — directly reduces how fast you can drain the OS backlog queue.

The worker pool receives connections

On the other side of that channel, a fixed pool of goroutines waits for work:

func startWorkers(n int, connCh <-chan net.Conn) { for i := 0; i < n; i++ { go func() { for conn := range connCh { handleConn(conn) } }() } }

Each goroutine pulls connections off the channel and calls handleConn. The pool size N is fixed — configured by the --workers flag. If all N workers are busy, the channel send in the accept loop blocks (since the channel is buffered but finite), applying natural backpressure.

Clean shutdown

Shutdown needs to happen in order:

  1. Receive the interrupt signal (SIGINT, SIGTERM)
  2. Close the listener — this causes Accept() to return an error, exiting the accept loop
  3. Close the connection channel — this causes the range connCh loop in each worker to exit
  4. Wait for all workers to finish their current connections (use a sync.WaitGroup)
Common mistake
Closing the channel before the listener causes a race: the accept loop might try to send to a closed channel and panic. Always close the listener first, wait for the accept loop to exit, then close the channel.

Putting it together — the skeleton of listener.go

func Run(port string, workers int) { ln, _ := net.Listen("tcp", ":"+port) defer ln.Close() connCh := make(chan net.Conn, workers) startWorkers(workers, connCh) // Handle SIGINT/SIGTERM in a goroutine, // then close the listener to unblock Accept(). for { conn, err := ln.Accept() if err != nil { break } connCh <- conn } close(connCh) // wg.Wait() — wait for workers to drain }
Think it through
Why is the connection channel buffered (size = workers) rather than unbuffered?
An unbuffered channel blocks the sender until a receiver is ready. A buffered channel of size N can hold N items before blocking. What does that mean for the accept loop when all workers are busy?
It gives the accept loop a small cushion. With an unbuffered channel, if all workers are busy, the accept loop immediately blocks on the channel send — which means it can't call Accept() and the OS backlog starts filling. With a buffered channel of size N, you can absorb a burst: accept up to N connections before any worker is free. The buffer is sized to workers because that's the maximum number of connections that could be "in flight" between the accept loop and the workers at any moment. Any larger and you're just wasting memory.
Think it through
What happens to a connection that's currently being handled by a worker when Close() is called on the listener?
The listener close affects Accept(). Does it affect existing net.Conn objects that were already returned by Accept()?
Nothing — existing connections are unaffected. ln.Close() only affects the listener socket, not the individual connection sockets that were already accepted. Workers holding active connections can finish handling them normally. This is why you need a sync.WaitGroup: after closing the listener and channel, you wait for all workers to finish their in-progress connections before the process exits. Without it, the process may exit while a worker is mid-response.
