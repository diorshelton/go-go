TCP & Connections

Before you can parse an HTTP request, you need to understand what's delivering those bytes to your program. That's TCP — and understanding it changes how you think about everything above it.

What is a connection, actually?

When someone says "the client sends a request to the server," that description skips the most important part. There's no single moment where bytes are teleported from one machine to another. First, a connection is established — a dedicated channel between two endpoints — and then bytes flow through it.

That channel is a TCP connection. TCP stands for Transmission Control Protocol, and it has one job: guarantee that bytes sent from one end arrive at the other, in order, without duplication. It handles retransmission, ordering, and flow control so that higher layers — like HTTP — don't have to.

Why this matters for go-go
In go-go, your server calls net.Listen and then Accept() in a loop. Each call to Accept() returns one TCP connection — one of these dedicated channels. Everything you do afterward (reading bytes, parsing the request, writing the response) happens on that single connection object.

The connection as a bidirectional pipe

The most useful mental model: a TCP connection is a bidirectional pipe. Once open, you write bytes into one end and they come out the other, in order, with no gaps. The pipe stays open until one side closes it.

This is important: the pipe is persistent. You don't open and close it for every chunk of data. HTTP/1.1 takes advantage of this — multiple requests can travel over the same connection, one after another. That's what keep-alive means. We'll get there in Module 2.

How Go exposes this

Go's net package wraps TCP connections behind the net.Conn interface. Once you have one, you interact with it using three methods:

type Conn interface { Read(b []byte) (int, error) // pull bytes off the wire Write(b []byte) (int, error) // push bytes onto the wire Close() error // close the connection SetDeadline(t time.Time) error // enforce a read/write timeout // ... plus SetReadDeadline, SetWriteDeadline }

Read blocks until bytes arrive or the connection closes. This is the most important behavior to internalize — your parser will call Read repeatedly, and each call waits for more data from the client. Write sends bytes. Close tears down the connection.

That's the entire API surface you'll use in listener.go and parser.go. No magic. Just reads, writes, and a close.

One connection per client, and the concurrency problem

Here's the constraint that forces go-go's design: if Read blocks, and you need to handle many connections simultaneously, you can't do it in a single goroutine. You need concurrency.

The naive answer is: spawn a goroutine per connection. But go-go uses a fixed worker pool instead. There's a reason for that choice — think it through below before we move on.

Think it through
If Read blocks waiting for bytes, what problem does handling connections one at a time in a single loop create?
Imagine 100 clients connect simultaneously. Connection #1 is slow. What happens to connections #2 through #100?
The server stalls. If you handle connections sequentially — accept one, read from it until it closes, then accept the next — a slow or idle client blocks every other client. Connection #2 cannot be served until connection #1 finishes. This is why concurrency is necessary: you need to Read from many connections simultaneously without any one blocking the others.
Think it through
go-go uses a fixed pool of N goroutines instead of spawning a new goroutine per connection. What does that limit protect against?
Goroutines are cheap — but not free. What happens if 100,000 clients connect and you spawn 100,000 goroutines?
Unbounded resource consumption. Each goroutine costs a few KB of stack memory and adds scheduler overhead. 100,000 goroutines consumes hundreds of megabytes just in stack space, and the scheduler's work grows with the count. A fixed pool caps this: N goroutines, no more. If more connections arrive than workers can handle, they wait in a channel. You trade some latency under extreme load for predictable, bounded memory usage. That's what the SPEC means by "explicit and observable concurrency."
