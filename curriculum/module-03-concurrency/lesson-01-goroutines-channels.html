Goroutines & Channels

Go's concurrency model is built on two primitives: goroutines (lightweight threads) and channels (typed pipes for passing values between goroutines). Understanding both is required before you can reason about go-go's worker pool.

Goroutines

A goroutine is a function running concurrently with other goroutines. You start one with the go keyword:

func handleConn(conn net.Conn) { // ... handle it } // In the accept loop: go handleConn(conn) // returns immediately, runs concurrently

The caller doesn't wait. go handleConn(conn) returns immediately and handleConn runs in its own goroutine, concurrently with everything else. The Go runtime schedules goroutines across OS threads using an M:N model — many goroutines, fewer OS threads.

Goroutines are cheap: a few KB of stack, dynamically growing. This is why spawning one per connection is viable for moderate load — but still not the right choice for bounded resource control.

Channels

Channels are typed pipes. You send a value into one end and receive it at the other. This is how goroutines communicate without shared memory:

ch := make(chan net.Conn, 10) // buffered channel, capacity 10 // Sender (accept loop) ch <- conn // send: blocks if channel is full // Receiver (worker goroutine) conn := <-ch // receive: blocks if channel is empty

Channels enforce synchronization: a send blocks until there's space; a receive blocks until there's a value. This blocking behavior is what makes channels safe for passing data between goroutines — no race conditions on the transfer itself.

Buffered vs unbuffered

An unbuffered channel (make(chan T)) has capacity 0. The sender blocks until a receiver is ready, and vice versa. This is a synchronization point — both sides must be ready simultaneously.

A buffered channel (make(chan T, N)) has capacity N. The sender can put up to N values in the channel without a receiver being ready — useful when you want to absorb bursts. Once the buffer is full, the sender blocks.

In go-go
The connection channel is buffered to workers: make(chan net.Conn, workers). The accept loop can enqueue up to workers connections before any worker picks one up. This small buffer absorbs connection bursts without stalling the accept loop.

Ranging over a channel

The idiomatic way for a worker to pull values from a channel until it's closed:

for conn := range connCh { handleConn(conn) } // exits when connCh is closed and drained

range on a channel blocks waiting for the next value, processes it, and repeats. When the channel is closed and empty, the loop exits. This is how workers know to shut down: the accept loop closes the channel after it exits.

Think it through
What happens if you send to a closed channel?
We close the channel to signal workers to stop. But what if the accept loop tries to send a connection after the channel is already closed?
Panic. Sending to a closed channel panics in Go. This is why the shutdown order matters: the accept loop must stop sending (exit its loop due to the listener being closed) before the channel is closed. In go-go: (1) close the listener → accept loop exits, (2) close the channel → workers drain and exit. Never close the channel while the accept loop might still be running.
Think it through
Two goroutines both receive from the same channel. A value is sent. Which goroutine gets it?
Think about how Go's channel scheduler works — does it guarantee fairness?
Exactly one goroutine gets it — which one is non-deterministic. Go's runtime selects one of the waiting receivers, but makes no ordering guarantee. This is exactly what you want for a worker pool: one connection, one worker, and the scheduler decides which idle worker handles it. You don't need to manage assignment explicitly — the channel does it.
