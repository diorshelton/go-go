Race Conditions & the Go Race Detector

A race condition happens when two goroutines access shared state simultaneously and at least one is writing. The result is undefined — not just "sometimes wrong." Go ships with a race detector that catches these at runtime.

What a race condition looks like

Consider a cache without any locking:

type UnsafeStore struct { data map[string]json.RawMessage } func (s *UnsafeStore) Get(key string) json.RawMessage { return s.data[key] // no lock } func (s *UnsafeStore) Set(key string, val json.RawMessage) { s.data[key] = val // no lock }

If goroutine A calls Set("foo", ...) while goroutine B calls Get("foo"), both are accessing the internal map state simultaneously. Go's map is not safe for concurrent access — this is a data race. The Go spec says: undefined behavior. In practice: crashes, silent data corruption, or reading half-written values.

The race detector

Go ships with a built-in race detector based on ThreadSanitizer. Enable it with the -race flag:

$ go test -race ./...
$ go run -race ./cmd/server/main.go
$ go build -race -o server ./cmd/server/main.go

When a race is detected at runtime, you get output like this:

==================
WARNING: DATA RACE
Write at 0x00c0001a4000 by goroutine 7:
main.(*UnsafeStore).Set(...)
/path/to/store.go:14
Previous read at 0x00c0001a4000 by goroutine 8:
main.(*UnsafeStore).Get(...)
/path/to/store.go:10
==================

It tells you the two goroutines, the exact lines of code, and which was the write and which was the read. This is what you run against go-go's tests to verify your mutex usage is correct.

The race detector only fires on execution paths that run
A race condition that only occurs under high concurrency won't be caught unless your test actually exercises that path. Always write tests that spawn multiple goroutines accessing the store simultaneously — not just sequential tests.

Race detector test for the store

func TestStoreConcurrent(t *testing.T) { s := store.New() var wg sync.WaitGroup // 50 concurrent writers for i := 0; i < 50; i++ { wg.Add(1) go func(n int) { defer wg.Done() key := fmt.Sprintf("key%d", n) s.Set(key, json.RawMessage(`"value"`)) }(i) } // 50 concurrent readers for i := 0; i < 50; i++ { wg.Add(1) go func(n int) { defer wg.Done() s.Get(fmt.Sprintf("key%d", n)) }(i) } wg.Wait() }

Run this with go test -race ./cache/.... If your mutex is correct, no race is detected. If you remove the locks, the race detector fires immediately.

Think it through
The race detector didn't fire on a single-goroutine test of your store. Does that mean there's no race condition?
The race detector instruments memory accesses at runtime. What does it need to fire?
No. The race detector only fires when it observes a race — two goroutines actually accessing the same memory concurrently at runtime. A test that calls Get() and Set() sequentially in one goroutine will never trigger it, even if the code has no mutex at all. The race detector is a dynamic tool, not a static analyzer. You must write tests that actually exercise concurrent access patterns to get meaningful coverage.
Think it through
Should you run go-go with -race in production? Why or why not?
The race detector adds memory and CPU overhead. Think about the trade-off.
Generally no — it's a development and testing tool. The race detector typically adds 5–10× memory overhead and 2–20× CPU overhead per memory access. For a production server under load, that's unacceptable. Use it during development, in CI, and in load tests. Once you're confident your synchronization is correct, build without -race for production. Some teams run a small percentage of production traffic through -race builds as a canary — but that's an advanced pattern.
