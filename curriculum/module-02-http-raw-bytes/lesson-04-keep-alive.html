Keep-Alive — Persistent Connections

HTTP/1.1 keeps TCP connections open by default. One connection, multiple requests. This is what drives the keep-alive loop in your worker — and it's where connection lifecycle management becomes non-trivial.

The problem keep-alive solves

In HTTP/1.0, every request required a new TCP connection: handshake, request, response, close. If a browser needed to load 30 resources from a server, that was 30 separate connections — 30 handshakes. Expensive.

HTTP/1.1 made connections persistent by default. The same TCP connection can carry multiple requests sequentially. The browser sends a request, gets a response, sends another request on the same connection, and so on. The connection stays open until one side signals it should close.

Client                                   Server
TCP connect (3-way handshake)
→ GET /keys/foo HTTP/1.1 →
                                                ← 200 OK ←
→ PUT /keys/bar HTTP/1.1 →
                                                ← 200 OK ←
→ GET /keys HTTP/1.1 →
                                                ← 200 OK ←
→ Connection: close →
TCP close

Three requests, one connection. Without keep-alive, that would be three handshakes.

The keep-alive loop in your worker

This is what makes go-go's worker design different from "one goroutine per request." Each worker handles one connection at a time, looping on that connection until it should close:

func handleConn(conn net.Conn, router *Router) { defer conn.Close() reader := bufio.NewReader(conn) for { // Set deadline before each request conn.SetReadDeadline(time.Now().Add(30 * time.Second)) req, err := parseRequest(reader) if err != nil { if !errors.Is(err, io.EOF) { writeError(conn, 400, "Bad Request") } return // connection dead or done } resp := router.Handle(req) writeResponse(conn, resp) // Close if client asked for it if strings.ToLower(req.Headers["connection"]) == "close" { return } } }

The loop runs until one of three things happens:

  1. Parsing fails — connection is dead or sent bad data
  2. Client sends Connection: close
  3. The read deadline fires (idle connection times out)
The deadline resets each iteration
Notice that SetReadDeadline is called at the top of the loop, before each parse. This is intentional: a client gets 30 seconds to start sending its next request. If it doesn't, the deadline fires, ReadString returns a timeout error, parsing fails, and the loop exits. This prevents idle connections from holding worker goroutines forever.

What your response must include

When you respond to a request on a keep-alive connection, your response must include Content-Length. Without it, the client can't know where the response body ends and the next response begins — it can't multiplex without this boundary.

If you're closing the connection after the response, include Connection: close in your response headers to notify the client.

Think it through
A worker is in the keep-alive loop, waiting for the next request. The client has closed the connection on its end without sending anything. What does ReadString return, and what should the loop do?
TCP sends a FIN packet when a side closes. What does Read() return when the remote side closes gracefully?
ReadString returns io.EOF. When the remote side closes the connection gracefully (TCP FIN), any Read() on that connection returns (0, io.EOF). This is not an error — it's the normal end-of-connection signal. Your loop should detect io.EOF, skip writing any response (the client is gone), and return from handleConn. The defer conn.Close() will clean up the server's side.
Think it through
In the keep-alive loop, the same bufio.Reader is reused across requests. Why is this correct, and what would go wrong if you created a new one each iteration?
bufio.Reader has an internal buffer. What's in that buffer between requests?
The reader's buffer may contain the start of the next request. bufio.Reader reads ahead — when you read one line, it might have read several more from the socket into its internal buffer. If you create a new bufio.Reader each iteration, those buffered bytes are lost: you'd try to read the next request from the socket, but the bytes are sitting in the discarded reader's buffer. Reusing the same reader preserves those buffered bytes across the loop.
