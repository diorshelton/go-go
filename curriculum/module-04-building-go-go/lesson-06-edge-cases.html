Defensive Edge Cases & Clean Shutdown

You have a working server. Now you need to make it correct under hostile or unexpected conditions. This lesson covers the scenarios that don't show up in the happy path but matter in production.

The edge cases you must handle

PARTIAL READ
Client sends only the first line then stalls. bufio.Reader.ReadString blocks. Your read deadline fires → return error → send 400 → close connection.
BODY TOO LARGE
Content-Length: 999999999 — more than maxBodySize. Reject before reading any bytes → return 413. Never allocate the buffer.
MALFORMED REQUEST LINE
SplitN returns fewer than 3 parts, or the HTTP version isn't HTTP/1.1. Return ErrBadRequest → send 400.
INVALID JSON BODY
PUT with Content-Length: 3 body xyz. json.Valid returns false → return 400. The cache never sees it.
UNKNOWN ROUTE
GET /notaroute falls through the router's switch → return 404. POST /keys/x matches path but not method → return 404 (or 405 — either is fine for go-go).
CLIENT DISCONNECT
Client closes connection mid-stream. ReadString returns io.EOF or io.ErrUnexpectedEOF. Neither is ErrBadRequest — just return without writing.

The complete handleConn error map

Every error ParseRequest can return, and what handleConn does with it:

func handleConn(conn net.Conn, router *Router) { defer conn.Close() reader := bufio.NewReader(conn) for { req, err := ParseRequest(reader, conn) switch { case err == nil: // happy path — fall through case errors.Is(err, ErrBadRequest): WriteError(conn, 400) return // connection is now dirty — close it default: // io.EOF, net.Error (timeout), or other I/O failure — just close return } resp := router.Handle(req) keepAlive := strings.ToLower(req.Headers["connection"]) != "close" WriteResponse(conn, resp, keepAlive) if !keepAlive { return } } }
Why return after a 400?
After a malformed request, the connection is in an unknown state. You don't know how many bytes the client has sent or plans to send. Trying to parse the next request on this same reader risks interpreting leftover body bytes as a request line. It's always safer to close after a parse error and make the client reconnect.

Clean shutdown — the full sequence

When the process receives SIGINT or SIGTERM, go-go must drain without dropping in-flight requests. Here's the full sequence:

  1. Signal arrives → goroutine receives it from quit channel → calls ln.Close()
  2. Accept() returns an error — not a client error, a listener-closed error. The accept loop breaks.
  3. pool.Shutdown() is called — this closes the connection channel (close(connCh)), signaling workers to stop taking new work
  4. Workers finish their current connection — each worker's for conn := range connCh loop exits naturally after the channel is drained and closed
  5. wg.Wait() returns — all workers have called wg.Done(), meaning all in-flight connections are complete
  6. Run() returns → main() exits → process terminates cleanly
What clean shutdown does NOT guarantee
Connections that are accepted but not yet submitted to the pool when the listener closes will be dropped. Connections in the pool's buffer channel that haven't been picked up by a worker will be dropped. Only connections actively being handled by a worker are drained. For go-go's use case, this is acceptable — graceful shutdown means in-flight requests complete, not that the queue is fully drained.

Running the race detector on the full server

Build and test with the race detector before declaring done:

# Run all tests with race detection go test -race ./... # Run the server itself under the race detector go run -race ./cmd/server/main.go --port 8080 --workers 4 # In another terminal — hit it concurrently for i in {1..20}; do curl -s -X PUT localhost:8080/keys/k$i -d '"val"' & curl -s localhost:8080/keys/k$i & done wait

If the race detector fires, it will print the exact goroutines involved and the memory address that was accessed without synchronization. The fix is always: add or correct a lock.

Think it through
You've built the full server. A colleague says "we should add a timeout so the server auto-shuts down if it's idle for 10 minutes." Where would you implement this, and what's the simplest approach?
In main(), using a context with timeout — but think carefully about what "idle" means. A global inactivity timeout is harder than it sounds: you'd need to track the last request time across all workers (shared state, needs synchronization), then fire shutdown when it's been idle. Simpler options: a deadline-based approach where a goroutine in main() watches a time.After and calls ln.Close(), or add idle detection per-connection by checking if the read deadline fires without any successful reads. The real takeaway: identify the exact definition of "idle" before writing code. "No requests in 10 minutes" and "no active connections in 10 minutes" are different invariants.
