response.go — Writing Valid HTTP

The response writer turns a *Response into bytes on the wire. It's the smallest component in go-go — but it's where correctness is most visible to clients.

What a response looks like on the wire

Before writing any code, look at exactly what you need to produce. This is what curl -v shows for a successful GET:

HTTP/1.1 200 OK ← status line Content-Type: application/json ← always JSON Content-Length: 13 ← byte count of body Connection: keep-alive ← or "close" depending on request \r\n ← blank line (CRLF) separating headers from body {"key":"value"} ← body bytes (no trailing newline)

Three invariants hold for every response go-go sends:

  • Content-Length matches len(body) exactly — not an estimate
  • Content-Type is always application/json — go-go only speaks JSON
  • Headers and body are separated by exactly \r\n (blank line)

The complete implementation

package server import ( "fmt" "net" ) func WriteResponse(conn net.Conn, resp *Response, keepAlive bool) { conn := "close" if keepAlive { conn = "keep-alive" } header := fmt.Sprintf( "HTTP/1.1 %d %s\r\nContent-Type: application/json\r\nContent-Length: %d\r\nConnection: %s\r\n\r\n", resp.Status, statusText(resp.Status), len(resp.Body), conn, ) conn.Write([]byte(header)) conn.Write(resp.Body) } func WriteError(conn net.Conn, status int) { body := []byte(fmt.Sprintf(`{"error":"%s"}`, statusText(status))) WriteResponse(conn, &Response{Status: status, Body: body}, false) } func statusText(code int) string { switch code { case 200: return "OK" case 400: return "Bad Request" case 404: return "Not Found" case 405: return "Method Not Allowed" case 413: return "Content Too Large" default: return "Internal Server Error" } }
Variable shadowing bug — spot it
The code above has a subtle bug: conn := "close" on line 8 shadows the conn net.Conn parameter. After that assignment, conn refers to a string, not the connection — conn.Write(...) at the bottom won't compile. The fix: use a different variable name, like connHeader := "close". This is a real trap in Go because := always creates a new variable in the current scope.

Why two Write calls?

You could concatenate header and body into one byte slice and write everything at once. Two writes is fine here because:

  • TCP coalesces small writes into one segment (Nagle's algorithm, or just network buffering)
  • The body is already a []byte — copying it just to append it to the header would be wasteful for large values
  • Clarity: header formatting and body writing are distinct responsibilities

If you needed strict performance, you'd use net.Buffers (scatter-gather I/O) to avoid any copies. For go-go, two writes is the right tradeoff.

Content-Length is a contract

When the client reads a response, it uses Content-Length to know how many body bytes to consume before the next response starts (on a keep-alive connection). If you write the wrong length:

  • Too small: the client reads only N bytes, then tries to parse the remaining body as the next response's status line. You get protocol corruption — every subsequent request on this connection will behave strangely.
  • Too large: the client blocks waiting for more bytes that never arrive.

This is why len(resp.Body) must be computed before writing headers, not hardcoded or estimated. The body is already in memory as a []byte, so len() is O(1) and exact.

Think it through
WriteError always passes false for keepAlive. Why is that the right call?
Error responses terminate the connection. When WriteError is called, something went wrong — bad request, parse failure, unsupported method. There's no guarantee the connection state is coherent enough to safely parse another request. Sending Connection: close tells the client this connection is done, and the handleConn loop will return after WriteError because the parse error caused it to exit. Even if the client ignores the header, the server won't read again from this conn — it's already returning from handleConn.
Think it through
The response writer doesn't check the error return from conn.Write(). Is that a problem?
Not a meaningful problem here. If Write fails (client disconnected, network error), there's nothing useful to do — you can't send an error response if writing is broken. The connection will be closed when handleConn returns. Ignoring Write errors in response writers is idiomatic in Go servers. The critical error handling is in reading (ParseRequest), where errors directly affect what you send back. On writes, you just close and move on.
